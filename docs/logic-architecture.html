逻辑架构文档

GRSAI NewAPI：OpenAI 兼容层到 GRS AI 上游的适配服务

这个项目是一个轻量 Go HTTP 服务。它对外暴露 OpenAI 风格的模型、聊天和图片接口， 对内使用配置好的 GRS AI API Key 请求上游服务，并负责可选客户端鉴权、参数默认值、尺寸映射、SSE 中继和统一错误整理。

运行入口 main.go
HTTP 路由 router/router.go
核心协议 JSON + SSE
默认端口 8080

阅读目标

看完后应能独立定位请求入口、改模型列表、增加接口和排查上游错误。

理解服务边界

知道哪些能力是本项目处理，哪些能力是透传给 GRS AI 上游完成。

掌握请求生命周期

从客户端请求、路由分发、handler 解析、client 转发，到响应写回形成完整链路。

识别扩展点

新增模型、请求字段、上游路径、鉴权策略时，知道应该改哪个目录。

总体架构

项目采用清晰的分层：配置加载、路由注册、业务处理、上游客户端、数据模型。

客户端 OpenAI SDK、curl 或业务服务，请求 /v1/*。
→
Router 显式 method/path 分发表绑定模型、聊天、图片路由，并统一处理 401/404/405。
→
Handler 解析请求、校验必填字段、补默认值、选择普通或流式分支。
Model 定义 OpenAI 兼容结构和 GRS AI 绘图结构。
↔
GRSAI Client 添加上游鉴权头，发送原始或转换后的 JSON 请求，处理响应、SSE 和上游错误。
↔
GRS AI 真实模型推理与绘图任务执行方。

为什么这样分层

这个服务本质是适配器，不需要复杂领域层。路由负责 URL/method 分发、可选客户端鉴权和基础错误外壳， handler 负责外部协议，grsai.Client 负责上游协议，模型结构集中放在 model 包。

当前架构特点

  • 没有数据库、队列或后台任务。
  • 聊天接口使用原始 JSON 透传，尽量保留 OpenAI 扩展字段和上游响应字段。
  • 图片接口会把 OpenAI 图片格式转换成 GRS AI draw 请求，并显式校验 n 和 response_format。
  • 配置 RustFS/S3 参数后，图片结果会先转存到对象存储，再把对象 URL 返回给客户端。
  • 上游 API Key 只在服务端使用；设置 PROXY_API_KEY 后，客户端请求也会校验 Bearer token。

请求链路

一次请求进入服务后，通常经过 5 个阶段。

1. 启动
config.Load() 读取 .env 和环境变量。
grsai.NewClient() 注入 baseURL 和 API Key。
按需创建 storage.RustFSClient，用于图片转存。
router.New(client, proxyAPIKey, imageStorage) 注册路由。
2. 路由
客户端访问 /v1/chat/completions 等路径。
显式分发表根据 method + path 命中函数。
未知路径、错误方法和鉴权失败直接返回 OpenAI 风格错误。
模型列表走静态 handler，聊天和图片走带 client 的 struct handler。
3. 处理
读取 body 或 multipart form。
聊天请求只解析 stream，图片请求反序列化到 model 结构。
校验 prompt、image 等必填字段。
补默认 model、size、n。
4. 上游
聊天使用原始 JSON 透传，图片构造 GRS AI draw 请求体。
设置 Authorization 和 Content-Type。
普通聊天读完整 JSON。
流式聊天或绘图读取 SSE。
5. 响应
普通聊天原样写回上游 JSON，图片使用 writeJSON。
聊天流直接转发上游 SSE 字节。
图片提取最终成功事件中的 URL；如启用 RustFS，则下载并上传后返回对象 URL。
错误统一包装为 OpenAI 风格 error.message/type/param/code。

数据模型

model 包是协议边界。外部格式和上游格式分开定义，避免 handler 里散落匿名结构。

model/openai.go

定义当前服务对外承诺的 OpenAI 风格结构。

  • 聊天请求和普通响应当前走原始 JSON 透传，避免裁剪 OpenAI 扩展字段。
  • ChatCompletionRequest、ChatCompletionResponse 和 ChatCompletionChunk 保留为兼容结构参考。
  • ImageGenerationRequest、ImageEditRequest 对应图片接口。
  • ErrorResponse 保持 {"error": ...} 外层格式，并支持 message/type/param/code。

model/grsai.go

定义上游绘图接口使用的结构。

  • DrawRequest 包含 prompt、image、size、quality、aspect_ratio。
  • DrawSSEEvent 对应上游绘图任务的进度事件。
  • DrawImageItem 保存最终图片 URL 和尺寸。
  • GrSAIError 保留 GRS AI 原生错误结构；实际错误解析主要由 grsai.APIError 和 parseAPIError 统一完成。
Go: 聊天请求透传的核心思路 
// Handler 只读取 stream 字段来决定分支，实际请求体仍原样转发给上游。
body, err := io.ReadAll(r.Body)
if err != nil {
    writeInvalidRequestError(w, "failed to read request body", "")
    return
}

var req struct {
    Stream bool `json:"stream,omitempty"`
}
json.Unmarshal(body, &req)

// 非流式响应也直接写回上游 JSON，避免丢失未知字段。
resp, err := h.Client.ChatCompletion(body)
writeRawJSON(w, http.StatusOK, resp)

流式处理

聊天流式接口是字节级中继；图片接口则是消费上游 SSE 后返回普通 JSON。

聊天 SSE 中继

当 stream=true 时，ChatHandler 调用 ChatCompletionStream， 该方法创建无总超时的 HTTP client，拿到上游响应后把 body 按 4096 字节块写给客户端，并调用 Flush()。

  • 响应头设置为 text/event-stream。
  • 当前服务不解析聊天 chunk 内容。
  • 上游返回非 2xx 时，会先读取错误 body，并尽量保留状态码、类型和 code。

为什么流式 client 无超时

http.Client.Timeout 是整个请求生命周期的总超时。对于长连接 SSE， 如果使用 180 秒总超时，长回答可能被服务端主动切断，所以流式聊天使用 Timeout: 0 的专用 client。

Go: 聊天流式中继的简化逻辑 
// 读取上游 SSE，并立刻写回当前客户端。
buf := make([]byte, 4096)
for {
    n, err := resp.Body.Read(buf)
    if n > 0 {
        w.Write(buf[:n])
        flusher.Flush()
    }
    if err == io.EOF {
        break
    }
    if err != nil {
        break
    }
}

图片任务

图片接口对外像 OpenAI Images API，对内转成 GRS AI draw 请求，并等待上游任务完成。

文生图

  1. 解析 JSON 到 ImageGenerationRequest。
  2. 校验 prompt 必填。
  3. 默认 model=gpt-image-2、n=1、size=1024x1024。
  4. 显式拒绝 n != 1，并限制 response_format 只能为空、url 或 b64_json。
  5. 调用 mapSize 转换 size 和 aspect_ratio。
  6. 调用 CreateImage，读取上游 SSE 直到成功。

图生图

  1. 根据 Content-Type 判断 multipart 或 JSON。
  2. multipart 文件会被读入并编码为 data:image/png;base64,...。
  3. 校验 image 和 prompt 必填。
  4. 默认 model=nano-banana-pro、size=1024x1024。
  5. JSON 和 multipart 都会校验 n 与 response_format，避免假装支持上游无法满足的 OpenAI 参数。
  6. 调用 EditImage 后统一写回 OpenAI 风格图片响应。

尺寸映射表

客户端输入 上游 size 上游 aspect_ratio
256x256、512x512、1024x1024 1K 1:1
1024x1792 2K 9:16
1792x1024 2K 16:9
1K、2K、4K 原样透传 空
未知格式 原样透传 空

错误处理

当前服务将自身校验错误和上游错误都包装成 OpenAI 风格的错误外壳。

请求解析错误

读取 body 失败、JSON 反序列化失败、multipart 解析失败，会返回 400。

业务必填缺失

图片接口缺少 prompt 或 image 时返回 400。

上游调用失败

GRS AI 返回非 2xx 时会尽量保留原状态码；SSE 失败事件和网络错误会返回 OpenAI 风格错误对象。

路由与鉴权错误

未知路径返回 404，错误方法返回 405，PROXY_API_KEY 校验失败返回 401。

JSON: 统一错误响应 
{
  "error": {
    "message": "Missing required parameter: 'prompt'.",
    "type": "invalid_request_error",
    "param": "prompt"
  }
}

扩展方式

这个项目的扩展通常是“改模型、加路由、补字段、增强上游 client”四类。

新增模型

修改 handler/models.go 中的 models 列表即可让 GET /v1/models 返回新模型。 如果新图片模型需要走特殊上游路径，还要修改 grsai/draw.go 的路径选择逻辑。

新增 OpenAI 兼容字段

聊天请求现在使用原始 JSON 透传，新增聊天字段通常不需要改结构体。图片请求仍会转换成 GRS AI draw 请求，如果需要支持新的图片字段，应在 model/openai.go 和对应 handler 中补映射。

新增接口路径

一般需要三步：在 model 定义请求/响应结构，在 handler 编写 HTTP 处理器， 在 router/router.go 注册 method + path。若要请求上游，则在 grsai 包添加方法。

启用当前服务鉴权

设置 PROXY_API_KEY 后，客户端请求当前服务必须携带 Authorization: Bearer ${PROXY_API_KEY}。未设置时保持本地开发友好的免鉴权行为。

增强稳定性

可在 grsai.Client 层增加重试、请求日志、上游超时拆分和 context 取消传播。 未启用 RustFS 时，图片 b64_json 会直接下载远程 URL；启用 RustFS 后，会复用转存时下载的图片字节。 生产环境仍可继续增强下载超时、对象大小限制和对象生命周期策略。

常见误区

这些点容易在二次开发或部署时踩到。

把它当成完整网关

当前项目是适配器，不是完整 API 网关。它支持可选客户端 Bearer 鉴权，但没有限流、审计、配额、租户隔离和缓存。 如果要暴露给外部用户，应结合网关策略一起使用。

以为图片接口立即返回任务 ID

上游 draw 接口虽然是 SSE 任务流，但当前服务会等待成功事件，然后返回图片 URL。 因此图片请求可能持续较长时间。

忽略 response_format=b64_json 的成本

未启用 RustFS 时，服务需要下载图片再转 base64；启用 RustFS 后，服务会先转存 RustFS，再基于同一份字节返回 base64。 两种模式都需要考虑远程文件大小、网络失败和请求耗时。

误改模型列表就以为上游一定支持

/v1/models 是当前服务声明的静态列表。真正是否能推理成功，还取决于 GRS AI 上游是否支持对应模型。

练习

如果你要熟悉代码，可以按这些小任务逐步上手。

练习 1：新增模型

在 handler/models.go 添加一个测试模型，启动后请求 /v1/models 验证返回。

练习 2：增加请求日志

在路由外层增加中间件，打印 method、path、耗时和状态码。

练习 3：启用鉴权

设置 PROXY_API_KEY，验证未携带或携带错误 Bearer token 时返回 authentication_error。

练习 4：验证 RustFS 转存

设置 RustFS 环境变量后运行集成测试，确认 tiny PNG 能上传并返回对象 URL。

练习 5：验证路由错误

请求未知路径、错误 method 和错误 Bearer token，确认分别返回 404、405、401 的 OpenAI 风格错误。

练习 6：单元测试

用内存 HTTP mock 或 httptest 覆盖 raw JSON 透传、图片参数校验和路由错误响应。

总结

项目主逻辑可以压缩成一句话：对外兼容 OpenAI，对内适配 GRS AI。

核心心智模型： 客户端只需要认识 /v1/models、/v1/chat/completions、/v1/images/*； 当前服务负责把这些 OpenAI 风格请求变成 GRS AI 能理解的请求，并把上游响应整理成客户端熟悉的格式。 聊天路径偏透传，图片路径偏转换，配置和上游鉴权集中在服务端完成。
